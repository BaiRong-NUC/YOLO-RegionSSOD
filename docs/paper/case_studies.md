# B2/P1 成功与失败案例

本组案例使用已经冻结的 **学生 seed0** B2/P1 完整验证预测，在新增 B2 seed1
结果出现前选定。它用于解释已有结果，不参与阈值调整，也不替代全验证集指标。

![B2 与 P1 的四类诊断案例](../../outputs/paper_cases_b2_p1_s0/cases_overview.png)

**图 4-1 建议图注：**相同验证图像上 B2 与 P1 的检测案例。每行从左到右为 GT、
B2、P1，黄色框或箭头表示关注位置。绿色为匹配到 GT 的预测，橙色为未匹配预测，
紫红色为未被匹配的 GT；GT 列白框表示其他标注。A 为 P1 检出而 B2 漏检的小目标，
B 为 B2 检出而 P1 漏检的小目标，C 为两者共同漏检的小目标，D 为 P1 的未匹配预测。
所有匹配先在完整原图上对所有尺度 GT 联合进行，再裁剪显示；评估参数为
conf=0.25、类别一致、IoU≥0.50、NMS IoU=0.70、max_det=500。

A 展示了当前操作点下 P1 对一个 B2 未匹配行人的补充检出；B 同时展示了 P1
并不保留 B2 的所有检出。C 中远处行人在两组中都未被匹配，说明仍有大量困难
小目标尚未覆盖。D 的橙框只表示未能按当前类别与 IoU 规则匹配标注，不据此断言
其对应区域一定是背景；定位偏差、类别错误和重复检测都可能产生未匹配预测。
这些案例不能独立证明某个损失开关的因果作用，也不能推广为所有类别的表现。

完整 548 图中，small GT 的匹配状态可分为：

分组计数，也不是 VisDrone 官方错误分析或 AP_small。

## 固定选图规则与复现

按冻结验证文件顺序扫描，并在每张图内按 A/B/C/D 的顺序检查尚未填充的类型；
选择该类型首个符合条件的 GT/预测索引。关注中心必须距原图边界至少 32 像素。
展示图像的文件名前缀（首个下划线之前）与图像 SHA256 均不重复。
这一约束只用于避免案例内容重复；没有修改原验证集。脚本不按改善幅度排名，
没有人工删除失败案例。由于规则优先取文件顺序靠前的样本，四个关注对象恰好
都是 pedestrian，不能称为覆盖全部类别或全部场景的代表性抽样。

在 `yolo` 环境、仓库根目录执行：

```bash
python scripts/build_detection_cases.py
python scripts/build_detection_cases.py --check
```

生成器只重放已有预测，不进行训练或推理。已有输出目录时拒绝覆盖；后续核验
使用 `--check`。原图使用相同 384×256 像素裁剪，统一放大 1.5 倍显示，不为任一
方法单独调整窗口、阈值或颜色。匹配框的绘制路径会核对其 GT 匹配状态与现有
`match_by_confidence` 评估实现一致。

图像、单行 PNG 与 `manifest.json` 位于忽略目录 `outputs/paper_cases_b2_p1_s0/`。
manifest 保存选图规则、完整验证事件计数、关注框索引、裁剪坐标、1106 个输入
哈希及输出图哈希。图像属于本地产物，不提交到 Git；在具备原数据和冻结预测的
环境按上述入口重新生成。总览 PNG 为 1776×1910 像素，带 300 dpi 元数据；没有
生成像素以外的新视觉内容。
